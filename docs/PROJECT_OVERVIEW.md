# Basic Incremental — Project Overview

The project as it is built right now (version 0.5.5): one entry per system, screen and data area, with what it does today, where it lives and which rule in `docs/DESIGN.md` it implements ("DESIGN §n"; UI rules are in `docs/UI_RULES.md`, art rules in `docs/ASSET_RULES.md`). It describes only what exists in the code. Plans, targets and open questions live in DESIGN.md.

**This file is rewritten in place.** Every PR that changes `src/` updates the entries it touches (add, change or delete them) so the file always equals the code. No history and no "removed" notes: a deleted feature simply drops out. Exception: a tiny direct-in-Code job with no behaviour change (typo, comment, one-line fix) puts the line `no overview change` in its PR description.

## Project shape

Windows desktop game, Electron + TypeScript, built with electron-vite; tests are vitest (`tests/`, `helpers.ts` has `plainContent`, `freshState`, `newGame`). Numbers use `break_eternity.js` (`Decimal`). Save format version 26 (`CURRENT_SAVE_VERSION` in `src/game/save.ts`; format 25 sent every dungeon back to floor 1 of Normal, "replay Normal first", and added the training levels, DESIGN §6; format 26 added the state of the balance update, see State below: each production job's main card became the worker of its first tree or mine and each dungeon's boss kills the stage kills of its Normal last floor).

| Folder         | What it is                                                                                                                                                                         |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/game`     | Pure game logic (no DOM, Electron or Node). The only door for the UI is `src/game/index.ts`.                                                                                       |
| `src/data`     | Content JSON (`content/*.json`), zod schemas and `loadContent`. The only door is `src/data/index.ts`.                                                                              |
| `src/main`     | Electron main process: window, IPC, save files, auto-update, logs.                                                                                                                 |
| `src/preload`  | The bridge (`window.api`) the renderer may call.                                                                                                                                   |
| `src/renderer` | The UI: shell, pages, stage effects, widgets, themes, sound and art.                                                                                                               |
| `tests`        | vitest suites for logic, data, view models and art helpers.                                                                                                                        |
| `scripts`      | Checks (`check-*.mjs`), the balance sim (`sim/`), art bake (`art/`) and screenshot scripts (`shoot-*.mjs`, `probe-app.mjs`).                                                       |
| `design`       | Exploration pages, option mockups, screenshots, pixel drafts (`design/pixel`), local references (never committed).                                                                 |
| `.claude`      | Optional helper agents (`ui`, `pixel-art`, `mechanics`), the `pixel-art` skill (with `references/style/`, the user's Keep + Learn style picks) and the shared permission settings. |
| `.github`      | `ci.yml` (lint, test, build on PRs and main) and `release.yml` (tag `vX.Y.Z` builds and publishes the installer).                                                                  |

**Contract between logic and UI.** The renderer imports game code only from `src/game/index.ts` and `src/data/index.ts`, never from files inside them; `src/game` never imports UI, Electron or Node. ESLint enforces both (`eslint.config.mjs`). The renderer has no game rules: adapters (`pages/*Adapter.ts`, `pages/*Model.ts`) turn state into view models. Dev cheats are the separate `game/dev` entry, not exported from `index.ts`; `npm run build` fails when a release bundle contains them (`scripts/check-release-bundle.mjs`).

**Dev profiles.** Dev builds share one save folder (`%APPDATA%\basic-incremental-dev`). Two dev apps at once autosave over each other, so give each its own: `BI_PROFILE=<name>` (or `--bi-profile=<name>`) uses `%APPDATA%\basic-incremental-dev-<name>`, `BI_USER_DATA_DIR=<folder>` uses that folder as is. Names are letters, digits, `-` and `_`; packaged builds ignore both (`src/main/devPaths.ts`, DESIGN §2).

**Commands.** `npm run dev`, `npm run lint` (eslint, prettier, `check-design`, `check-workflow`), `npm run typecheck`, `npm test`, `npm run build`, `npm run sim -- --hours 40` (balance sim, DESIGN §14; it plays the shipped portals, the Legacy Gate closed, and prints pulls per hour; `--seeds 20` for balance PRs, `--profile active|idle|both`, `--step 5` for the first 2 h and `--late-step 15` after, `--strict`), `npx tsx scripts/sim/timeline.ts` (one run row by row), `npx tsx scripts/sim/rarity.ts` (rarity gaps).

## Scripts and CI

- `scripts/check-design.mjs`: every rule in `docs/DESIGN.md` and `docs/UI_RULES.md` has a status tag, no amendment-style sections.
- `scripts/check-workflow.mjs`: a PR that changes `src/` must change this file or say `no overview change` in its description; nothing but a README may remain in `docs/plans/` on main (`CLAUDE.md`, Workflow).
- `scripts/check-cards.mjs`, `check-dungeons.mjs`, `check-pixel-scale.mjs`, `check-release-bundle.mjs`, `a11y-*.mjs`: content, pixel-scale, bundle and accessibility checks.
- `scripts/sim/`: balance sim playing the real game logic against the pacing targets (DESIGN §14), with target ranges, the spread and worst seed of each milestone, the band check (median within 25% of the target, worst seed within 2×), an idle profile beside the active one (a check-in every 30 min, 8 h offline a day on the game's own offline progress), the median DPS per quarter hour, the median Card Portal and Wardrobe Gate pulls per hour, milestones for the first Hard and Nightmare clears and Dungeons 4 to 6, a sim player that uses every system of the balance update (DESIGN §14 The sim player's choices: the hardest-hitting lead `chooseLead`, the build order `buildOrder` that the wishlist `markWishlist`, star dust `spendStarDust` and shard copies `spendShards` serve, workers and second slots by value `workerPicks`, the forge `forgePlan`, tool lines `toolGain`, skills `nextSkill` and `chooseRespec`, Core farming on the best tier `fastestFarm`, cheap stage stars `starFarm`, overflow `chooseOverflow`, autobuyers `chooseAutomation`, and the cash-in rule of `ascendNow`), a progress report (`formatProgress`: hours to a maxed weapon or the best weapon, stage star levels and chests, skill points, star dust and workers at set hours; the typical run's fights over time), and per run the time to its first 5 run milestones (Money earned since the Ascension, 10K to 100M) with the Ascension guard that names runs slower than the run before (DESIGN §6); `rarity.ts` prints the rarity gaps (base, fresh, free stars, top tier) and fails when a higher rarity does not beat a lower one (DESIGN §5).
- `scripts/shoot-*.mjs` (`shoot-production.mjs`: the Production page with workers and the open worker picker; `shoot-production-mechanics.mjs`: tools, depth, forge and a lucky strike), `probe-app.mjs`, `probe-attack-speed.mjs` (measures the attack animation for a dagger and a hammer lead), `demo-progression.mjs`: screenshots and probes of the running app.
- `scripts/art/picker.mjs`: writes the interactive picker page (labelled pictures, Keep, Learn, Copy list) for every choice between pictures (`CLAUDE.md`, Workflow).
- `.github/workflows/ci.yml` runs `npm run lint`, `npm test` and `npm run build` on every PR and on pushes to main; `release.yml` publishes a GitHub Release when a `vX.Y.Z` tag is pushed (`RELEASING.md`).
