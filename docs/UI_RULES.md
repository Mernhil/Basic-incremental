# Basic Incremental — UI Rules

The one document for the interface: screens, layout, the shell, tooltips, on-screen copy, themes, responsive and device-pixel rules, and the conventions the `ui` agent follows. Read it before any UI change. Art (sprites, palettes, effects, animation) is in `docs/ASSET_RULES.md`; game rules and numbers are in `docs/DESIGN.md`.

## How this document works

Same rules as `docs/DESIGN.md` ("How this document works"): one version of each rule, every rule starts with a status tag (`[Built]`, `[Differs]`, `[To build]`, `[Default]` or `[Default · in game]`, `[Proposed]`), a change rewrites the rule where it lives, tags move with the code in the same PR, only the user decides (gaps are written as `[Default]` and listed under Open questions), and a changed or dropped rule gets one dated line in the Changelog. `npm run lint` runs `scripts/check-design.mjs`, which checks this file too. Section references like "DESIGN §5" point to `docs/DESIGN.md`.

## 1. Working conventions

- [Built] **One UI rulebook.** This file is the only document for screens, layout and UI conventions. Art rules are in `docs/ASSET_RULES.md`; the game design is in `docs/DESIGN.md`. Read this file before any UI change.
- [Built] **Who builds UI.** UI lives in `src/renderer/**` outside the art folders and in `design/**` outside `design/pixel`; the optional `ui` agent (`.claude/agents/ui.md`) can help. Sprites and effects are art (`docs/ASSET_RULES.md`), rules and numbers are in `src/game` and `src/data`. A screen that needs a value the game does not expose yet gets the value added to the game side first (types wanted and why), not a UI-side workaround.
- [Built] **Five options first.** A design, UI or graphics brainstorm in the Claude Desktop home chat shows the user 5 options that differ in ways that matter (layout, colour, density, motion, ornament) as mockups or screenshots, and the user picks before the final version is built. Small direct jobs in Code need no options. Options are never merged into `main`.
- [Built] **Skills.** UI work uses the frontend-design skill and the Design plugin skills (critique, design system, accessibility, UX copy).
- [Built] **Game data through public entry points.** The renderer imports game code only from `src/game` and `src/data` index files, never from files inside them (ESLint enforces it).
- [Built] **Adapters, no rules.** Display logic lives in adapters (`pages/*Adapter.ts`, `pages/*Model.ts`) that turn game state into view models. No game rules in the renderer.
- [Built] **Whole pixel scales.** Layouts that hold pixel art size it with `src/renderer/src/ui/pixelScale.ts` and `pixelFit.ts` so every sprite is a whole number of device pixels per art pixel at 100%, 125%, 150% and 200% (the rule itself is Clean pixels, ASSET_RULES.md §5). A layout that cannot fit the wanted scale takes the nearest whole one and reflows.
- [Built] **Verify UI changes.** `npm run lint`, `npm run typecheck`, `npm test` and a run or screenshot of the changed screen come before saying it is done; one screenshot set per PR.
- [Built] **Branches.** UI work goes on a branch `ui/<task>` in its own worktree, with a PR and green CI (GitHub workflow in `CLAUDE.md`).

## 2. Interface and screens

- [Built] **Shell look** (user, 2026-11-10). The table and every full view use the starter table's pixel-frame shell (DESIGN.md §8).
  - Panels are pixel frames: a dark edge with notched corners, a light top edge and a dark bottom edge, and no rounded corners. The frame step is a whole number of device pixels (about 4 CSS px at 100%).
  - Buttons have the same notched shape: gold when they can be used, dark plum when not.
  - Pixelify Sans is used only at 18 px and up, for headings and large numbers. All other text, small numbers included, is Atkinson Hyperlegible.
  - Colours, fonts and frame values are table tokens (ASSET_RULES.md §6), so another table item can re-skin all of it.
  - The floating-number cosmetics are not part of the shell and keep their own look.
- [Built] **One table, no pages** (user, 2026-11-11: layout 1a, "one table, no pages"; the table is mockup 4a, the full views 4b to 4n in `design/options/ui-layouts/`). The game has one screen, the table. Every part of the game is a pile, a wing or the dungeon window on it, and a click on one fans it out into its full view over the table. There is no sidebar, no page list and no Home page: the table is home.

- [Default · in game] **Toasts** (Claude, 2026-11-11, table update fix pass: achievement toasts stacked bottom-right and covered the last piles of the dock and part of open views). Toasts hang from the header's lower edge as one column centred on the table, 280 px wide at most (narrower on a narrow window), newest at the bottom, at most 3 at once with the oldest leaving first, each for about 4 s. They never sit over the dock or the header, and at 280 px they sit in the empty middle of a view's title bar (← Table at the left end, the view's own controls at the right; checked on the Cards view at 1280 × 720), so no pile, no title-bar control and no header control is under one. The lower toasts can lie over the top centre of a view's body for those seconds; a toast takes no click, so what is under it stays usable. They arrive on `--deal-dur` and `--deal-ease` from 16 px above and 92% size, and leave on `--deal-exit-dur` and `--deal-exit-ease`; under reduced motion they only fade in and out over `--deal-fade-reduced` (Motion E tokens below).
- [Built] **A full view** covers the table under the header, which stays. It has a title bar with a **← Table** button, the view's name in the display font and, at the right end, the view's own controls (the ×1 / ×10 / ×100 / Max toggle on the Logging and Mining views). Its content scrolls inside it. One view is open at a time: opening another (a goal, a link inside a view) replaces it.
- [Built] **Opening and closing a view** (user, 2026-11-11: every tile, wing and the dungeon window opens its full view; click, Esc or back closes it). A click on a pile, on a wing, or on the dungeon window anywhere that is not one of its own buttons opens its view. **← Table** and **Esc** close it.
- [Default · in game] **View keys and focus** (Claude, 2026-11-11). The window and each wing also have an open button in a corner for the keyboard; the mouse's back button and **Alt + ←** close a view like Esc. Esc first closes whatever sits above the view (a tooltip, the Details panel, the reward track, the goal list, a card popped out of a fan, a dialog) and only then the view. On open, keyboard focus moves to the view's title; on close it returns to the pile, wing or window that opened it. Every pile is a button with its name as its accessible name, reachable with Tab. Ctrl+Shift+G (the dev gallery) and Ctrl+Shift+D (dev cheats) keep working.
- [Built] **Header bar.** Left to right: the account level with its XP bar (it opens the reward track), the **Goals** button, Money and the two scrolls (Summon and Glamour) each with its rate, the **Details** button and the mute toggle. Everything else (gems, Cores, Frost Sigils, Glimmer Dust, Facet Shards, Starlight) sits behind Details, grouped as tree materials, mine materials, dungeon materials and prestige, each with its amount, rate, mastery and use; coins of those resources fly to the Details button. Money is the largest number in the header, in the display font. Money counts in coins (DESIGN §3 Coins): the chip shows the count, the coin's name and the coin tinted to match.
- [Built] **Goals are a header button** (user, mockup 4a: no goals panel on the table). The button reads "Goals" and how many goals are shown; a click drops the goal list down under it (the next 1–3 goals with their bars and estimates, DESIGN §10). A click on a goal closes the list and opens the view the goal belongs to. Esc or a click outside closes the list.
- [Built] **Motion E, "dealt from the deck"** (user, 2026-11-11). Things slide in one by one from where they came from, on a calm curve with a long stagger: a view is dealt out of the pile, wing or window that opened it, and goes back into it when it closes.
- [Default · in game] **Motion E tokens and moments** (Claude, 2026-11-11, from the user's direction above). The tokens are CSS variables on `:root` in `src/renderer/src/table/motion.css`, and every view uses them through `table/motion.ts`:
  - `--deal-ease` `cubic-bezier(0.22, 1, 0.36, 1)`, a calm ease-out, for everything that arrives; `--deal-exit-ease` `cubic-bezier(0.4, 0, 1, 1)` for what leaves.
  - `--deal-dur` 440 ms for one dealt item. `--deal-step` 90 ms before the second item, each later gap 10 ms shorter and never under `--deal-step-min` 40 ms. At most `--deal-max` 7 items are dealt one by one; the rest arrive with the seventh.
  - `--deal-scale` 0.92: a dealt item starts at 92% of its size and transparent, moved toward the place it came from (`--deal-reach` 0.6 of the way).
  - `--deal-exit-dur` 220 ms: a closing view leaves all at once (no reverse stagger), shrinking toward the pile, wing or window it came from, and fades.
  - `--deal-fade` 180 ms: the view's backdrop only fades; it never moves.
  - **Opening a view:** the backdrop fades in; the title bar is dealt first, then the view's sections (the elements the view marks `data-deal`, else the page's top-level blocks) one by one, each sliding from the opener toward its place.
  - **The table at launch:** the dungeon window rises 24 px into place first, the wings slide in from their own sides, then the piles are dealt left to right from the left end of the dock. Welcome back, when it shows, deals after the table.
  - **Content is usable at once:** nothing waits for an animation to be clicked, and opening or closing mid-deal stops the deal where it is and starts the new one from there.
  - **Reduced motion** (Windows' setting or Settings → Display): nothing slides, scales or staggers; a view fades in over 120 ms and closes at once, and the table appears complete.
  - Only `transform` and `opacity` animate, through the Web Animations API, never layout properties.
- [Default · in game] **Table layout and scale** (Claude, 2026-11-11). Sizes are CSS px; at 150% Windows scale every CSS px is 1.5 device pixels and pixel art keeps whole device-pixel scales (Whole pixel scales, §1).
  - Header 64 px. Dock 132 px. The wings are 216 px wide with 16 px from the window's edges; the dungeon window takes the width between them, with 16 px gaps.
  - At 1280 × 720 CSS px (a 1280 × 720 window at 100%, or a 1920 × 1080 window at 150%) the dungeon window is about 816 × 492.
  - Below 1180 px wide the wings narrow to 184 px and drop the worker and depth line; below 700 px tall the dock is 104 px high, with smaller stacks and no hint line.
  - The smallest window is 1024 × 640 (the Electron window's `minWidth` and `minHeight`); the table fits it without scrolling, and a full view scrolls inside.

Production, fighting and drop upgrades all sit in the two panels, in the order the shelf gives (affordable first). - [Built] **The team as a hand** (user, 2026-11-10 and 11; replaces the loadout fan of the Hero fan arena). The fighting team shows as the duel's hand (DESIGN §6 What the duel shows): the four cards side by side along the bottom, overlapping, the outer ones a little lower. Cards keep whole device-pixel scales and nothing is rotated, so the art stays crisp (ASSET_RULES.md §5). A hover or focus on a card shows its skill, role and health. Only the fighting loadout is a hand (logging and mining cards are workers, DESIGN.md §4).
- [Built] **Duel motion** (DESIGN §6 What the duel shows; motion E). A card that hits hops up with a glow in its colour, and the enemy card shows the equipped attack's code-drawn slash; nothing else plays on the enemy. A card's skill slides in as a compact plate from the left beside the enemy card, never over it. The enemy's attacks: the enemy card dips toward the card it hits, which shakes and shows a red number; before a slam the edges of the fight pulse (DESIGN §6 Boss attack pattern) and a slam flashes once. A knocked-out card fades to grey and stays grey until the floor is won. After a kill the enemy card drops away, the hand takes two steps (the walk) and the next enemy is dealt from the face-down deck. A team knockout shows its countdown over the hand. A Challenge's end shows a Victory or Defeat plate under the top plate. Drops spill from the enemy card and fly to the header; a rare drop gets a light beam and a toast. Only transform and opacity animate.
- [Built] **Production field.** Every strike shows "+n" off its tree or mine and the coins fly to the header; a harvest burst is a wave with one big total. The worker nudges toward its tile by its pattern. Reduced motion drops lunges, shakes and flashes.
- [Built] **Numbers.** Header counters roll smoothly and pulse when coins land. Floating numbers use the number style, attack and tick cosmetics, never hardcoded looks; their size follows the hit against the current average, and crits and signature attacks look different. The starter style is sticker numerals: chunky digits with a white outline, a drop shadow and a tilt, bouncing in place.
- [Built] **Buying.** Every buy button previews its effect (for example "DPS 12 → 13, time-to-kill 11h → 2h"). One ×1 / ×10 / ×100 / Max toggle at the right end of the Logging and Mining views' title bars sets how many levels every level line buys (DESIGN.md §4); affordable buttons glow and a small bar fills toward the next affordable level.
- [Built] Max buys as many levels as are affordable (at least one) and otherwise shows the next level; a ×N buy buys exactly N or nothing.
- [Built] **Welcome back.** After offline progress, a card fan deals one small card per category (time away and the cap, resources, kills, knockouts, drops, card XP and levels, mastery tiers), then Collect sends the coins to the header.
- [Built] **Performance.** At most about 30 popups at once, rapid numbers merged, animation paused when the page or window is hidden, one shared animation loop. Under reduced motion: no shake, flash or slow-down, and numbers fade in place.
